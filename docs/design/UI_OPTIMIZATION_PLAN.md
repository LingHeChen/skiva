## 1. 本轮调整

保留已认可的暖白、灰绿侧栏与橄榄绿强调色。本轮重点是工具的操作结构和专用组件：用户进入具体仓库即可读内容、查提交、看流水线；发布详情直接呈现快照内容、差异、渠道与操作。

上一版的概览统计和大步骤引导不再占据默认首页。默认打开 finance-skills 的文件工作区。新手说明收进“使用指引”，频繁操作留在对象附近。

**本轮不新增“项目”后端模型。** 界面以已有仓库作为内容工作上下文，发布快照、渠道、Profile 仍然归属组织。跨仓库的完整发布集合继续得到保留。

## 2. 参考依据与取舍

### GitLab：在浏览中保留仓库上下文

GitLab 的文件树支持目录结构浏览、文件搜索和切换时保留目录上下文；本方案采用左侧文件导航、右侧内容区与当前引用提示。参考：[GitLab File tree browser](https://docs.gitlab.com/user/project/repository/files/file_tree_browser/)。

GitLab 的提交视图把修改内容和关联流水线连接起来；本方案将提交 SHA、提交说明、文件差异、流水线入口放在同一仓库上下文中。参考：[GitLab Commits](https://docs.gitlab.com/user/project/repository/commits/)。

不引入 GitLab 完整的议题、合并请求和任意 CI 执行体系。这些超出 Skiva 当前职责。

### Vercel：以一次发布作为可检查的对象

Vercel 的部署管理提供项目内记录、筛选和手动提升操作；本方案采用紧凑发布记录、独立快照详情和直接可达的渠道操作。参考：[Vercel Managing Deployments](https://vercel.com/docs/deployments/managing-deployments)。

Vercel 区分构建日志与运行日志；Skiva 原型只设计静态校验运行的诊断查看，不据此宣称系统已有 Agent 运行日志。参考：[Vercel Logs](https://vercel.com/docs/logs)。

以上是对公开官方文档所述交互的借鉴，不代表已进入它们的登录控制台逐像素复刻。

### ui-ux-pro-max 的应用

使用 `developer tools dashboard dense` 生成建议，再以显式 `product: developer tools` 校正产品匹配。首个聚合结果中的企业官网 Hero / Sales 模式不适用，未采纳。校正结果命中 Developer Tool / IDE：采用极简网格、明确的信息层级、代码区与终端区；保留用户已认可的配色，不机械替换为蓝色或全黑界面。

另检索 `keyboard focus modal`，落实可见焦点、原生 dialog、键盘命令选择及关闭行为。风格密度以 8/10 为方向，控件强调清晰边界与紧凑操作；移动端增大操作区域。

## 3. 信息架构

```text
组织工作空间
├─ 仓库列表
│  └─ 当前仓库
│     ├─ 概览：提交与 README
│     ├─ 文件：引用选择 / 文件导航 / 预览 / 源码
│     ├─ Skills：本仓库候选版本
│     ├─ 流水线：阶段与诊断
│     └─ 设置：仓库扫描范围
├─ 发布：组织级快照列表
│  └─ 快照详情：内容 / 差异 / 操作记录 / 渠道推进
├─ Agent 接入：Profile / 模式 / 目标快照
└─ 审计记录
```

- 顶栏表达组织和当前上下文，支持命令搜索。
- 侧栏只有高频组织入口与仓库快捷入口。
- 仓库内使用横向标签，避免为同一对象频繁跨导航查找信息。
- 原型使用 hash 路由，支持深链接及浏览器前进 / 后退。正式版本映射到现有 Next 路由，保留旧 URL 兼容跳转。
- 成员、角色、安全策略与个人账户仍需保留在正式应用；本轮原型不展开全部管理页面。

## 4. 专用组件设计

| 组件               | 作用                                   | 原型可操作内容                                       |
| ------------------ | -------------------------------------- | ---------------------------------------------------- |
| 仓库上下文栏       | 标明仓库、来源与可见性，操作有明确目标 | 切换两个仓库；打开克隆命令                           |
| Git 引用选择器     | 浏览某个引用的内容                     | main / release 分支切换，报销额度随之变化            |
| 提交信息条         | 文件内容与版本来源关联                 | 作者、SHA、提交说明、复制 SHA、历史对照              |
| 文件浏览器         | 在目录和内容之间保持上下文             | 展开 / 收起 skills、文件选择、当前文件高亮           |
| Skill 阅读器       | 明确区分内容阅读和源码检查             | 格式化预览 / 带行号源码 / 复制内容 / 参考文件跳转    |
| 上下文检查区       | 展示与当前仓库有关的信息               | 来源、Skills 数、流水线、组织渠道、维护者            |
| 发布记录行         | 以一次发布为对象扫描记录               | 状态点、快照短 ID、来源、渠道、筛选、详情跳转        |
| 快照详情           | 当前状态和操作就近呈现                 | 完整集合、差异、记录、Canary / Stable / 回滚         |
| 发布抽屉           | 保留工作上下文，集中完成内容审阅       | 完整集合勾选、版本选择、双栏差异、移除提示、确认创建 |
| 双栏差异查看器     | 对照基线与候选                         | 行号、旧 / 新提交标识、增删背景；窄屏上下排列        |
| 流水线阶段选择器   | 从总状态进入具体检查步骤               | source / discover / validate / artifact 切换         |
| 日志查看器         | 查看与定位校验诊断                     | 深色等宽输出、时间、搜索、Error 筛选、复制、文件定位 |
| 命令搜索           | 快速跳到页面、文件或动作               | ⌘/Ctrl K、键盘上下选择、Enter、Esc                   |
| 范围明确的配置表单 | 修改配置前理解影响范围                 | 根目录校验、就地错误、模拟保存；组织策略只读说明     |

专用组件的差异不仅是颜色。它们拥有各自的信息结构、状态、快捷操作和键盘行为。公共 Button / Badge 只承担基础表达，不再用统一卡片承载所有内容。

## 5. 关键流程

### 浏览与理解内容

进入仓库 → 选择引用 → 文件树选中 SKILL.md → 预览规则 → 查看源码 / 参考文件 → 定位提交与流水线。

预览中展示的报销规则是该示例 Skill 的内容表达。正式产品需要通用 Markdown 渲染，不应为任意 Skill 自动推断“审批额度”等业务字段。若希望统一生成此类结构化摘要，需要定义元数据契约并处理解析失败。

### 从仓库开始发布

准备发布 → 抽屉载入组织 Stable 的完整集合 → 仅替换目标 Skill → 同屏检查差异与移除项 → 审阅确认 → 创建快照 → 进入快照详情。

抽屉中明确显示不同仓库来源，避免把仓库级入口误解成仓库独立渠道。创建快照仍不改变任何渠道。

### 交付与回滚

快照详情 → 推进 Canary（填写原因）→ 人工验证 → 推进 Stable → 必要时回滚 Stable 到历史 #023。

推进保持同一快照。生产实现继续使用 generation 和幂等键；并发冲突必须重新获取现状、重新预览。pinned 客户端不会自动切换。原型人工验证记录仅存内存，不构成真实生产门禁。

### 排查校验失败

流水线 → 切换失败示例 → 选静态校验阶段 → Error 筛选 / 日志搜索 → 文件与规则 ID → 定位 SKILL.md → 通过 Git 修复并再次提交。

“模拟重新校验”提供运行中的反馈，结果仍来自示例状态，不实际运行 Git 或校验器。

## 6. 视觉调整

- 侧栏由 226px 收紧到约 210px，仓库工作区成为主视觉。
- 标题从营销式大句改为对象名称；辅助说明保持一句。
- 面板圆角约 6px，控件约 5px，主要靠分隔线和状态组织层级。
- 普通数据用中性色，橄榄绿用于选中、主要操作和通过；琥珀色用于待验证 / 固定版本提醒。
- 技术字段使用等宽字体；源码与诊断保留行 / 时间信息。
- 文件预览、差异、控制台分别使用适合任务的组件；没有虚构趋势图。
- 主界面继续浅色，日志组件为局部深色。全局深色主题暂不在本原型中展开，正式改造仍需保留现有能力。

## 7. 与现有后端的对应关系

已核对 `router.go`、托管仓库前端组件与策略定义；下表区分现有能力与原型演示。

| 界面能力                   | 已有基础                                                                | 落地边界                                                                             |
| -------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 托管仓库文件 / 提交 / Diff | `/repositories/{id}/commits`、`tree`、`diff` 及已有 `ManagedRepository` | 可以复用；需将现有浏览数据转为交互组件，处理截断和路径边界                           |
| 分支选择                   | 当前浏览支持引用 / 提交参数                                             | 核对引用枚举、返回字段与权限；原型只有两个固定引用                                   |
| 外部仓库完整浏览           | 已有同步与候选版本                                                      | 不能假设托管浏览接口支持外部来源；优先浏览已构建 Skill 版本，完整 Git 浏览需另行实现 |
| Skill 源码与差异           | Skill version tree / content / diff                                     | 可复用；版本与路径必须固定，不使用浮动分支替代发布版本                               |
| 发布抽屉与渠道操作         | preview、releases、channels、generation、幂等机制                       | 主要前端重组；继承完整集合需核对快照详情字段                                         |
| 流水线阶段与诊断           | 固定步骤、diagnostics                                                   | 可转换为按阶段的诊断查看器；原型时间化日志为示例，不代表已有完整流式 stdout          |
| 日志全文检索 / 实时日志    | 需核对现有数据覆盖                                                      | 首期对已返回诊断做筛选；流式日志与持久化日志另行定义                                 |
| 仓库根目录                 | repository skillRoot 与 `.skills-platform.yaml`                         | YAML 实际结构为 `skills.root`，保持组织策略优先级与现有权限                          |
| 人工验证记录               | 原型内存                                                                | 若要求持久化、多人审核或发布门禁，必须增加后端记录和授权                             |
| Agent 目标快照             | Profile / channel 配置                                                  | 可展示目标；实际挂载、在线、上下文生效不能由目标反推                                 |

完整 Git 文件浏览在托管与外部来源上的覆盖可能不同，正式界面应显示明确来源状态和能力边界，不能用静态页面掩盖接口缺口。

## 8. 实施建议

1. **仓库工作区与组件基础**：顶栏、导航、路由兼容、文件 / 提交浏览、源码与 Markdown 预览。先连接已有托管仓库 API。
2. **发布记录与抽屉**：完整集合继承、真实 preview、差异、快照详情、渠道操作、冲突处理。复用原有鉴权和审计。
3. **诊断与接入**：静态步骤、诊断筛选、文件跳转、Profile 与客户端的目标视图；明确未获取的实际状态。
4. **管理与回归**：补齐成员、权限、密钥生命周期、组织设置、主题、空状态、错误状态和旧 URL；进行 E2E 与无障碍验收。

建议按功能连接真实接口，而不是一次替换整个 `console.tsx`。文件浏览、发布、诊断应各有独立状态与数据适配层，避免跨页面筛选串扰。

## 9. 原型范围与检查

原型为一个自包含 HTML，无网络字体、图标 CDN 或构建依赖。数据与状态仅存在当前页内存；刷新会重置。`prototype-v1.html` 保留上一版供比较。

已覆盖的体验路径：

- 文件预览 / 源码、分支对照、文件切换。
- 发布抽屉、完整集合、Canary、人工确认、Stable 与回滚。
- 流水线失败、搜索日志、复制与文件定位。
- 命令搜索、键盘选择、深链接与浏览器后退。
- 窄屏仓库、发布、Agent 和设置布局。

尚未展开：完整 Git 编辑器、真实终端、创建 PAT、角色切换、完整组织管理。点击“接入仓库”展示模式选择及示例仓库，不创建真实对象。

本轮需要确认：仓库中心的工作方式是否符合你的习惯；文件 / 差异 / 日志组件是否足够直接；发布抽屉是否比独立多步页面更顺手；当前信息密度是否合适。确认后再把设计接入正式页面。


## 10. 正式前端落地（2026-10-21）

- 使用 shadcn new-york 组件源码，注册配置位于 apps/web/components.json；公共控件由 components/ui 提供，暖白 / 橄榄绿和深色主题由 globals.css 统一定制。
- Button、Card、Badge、Input、Checkbox、NativeSelect、Textarea、Label、Table、Tabs、Dialog、Sheet、Command、Collapsible、Skeleton 等组成正式控制台。旧表单通过 FormInput 适配器接入 shadcn Checkbox，保留既有 API 行为。
- 仓库工作区接入 Git 引用、目录树、固定提交文件读取、源码 / Markdown 预览、历史、Skills、流水线及完整设置。
- 发布抽屉继承 Stable 完整集合，支持版本选择、差异审阅、移除提示、服务端预览与确认；快照详情提供内容、差异、渠道和记录。
- 流水线展示真实阶段诊断；Agent 面板区分上报快照、渠道目标与 pinned 模式。原有权限和管理操作保留。
- 新增 GET /repositories/{id}/file，复用仓库 ACL，验证路径与提交，对文本预览限制 256 KiB，拒绝二进制预览；外部仓库继续使用构建产物浏览。
- 原型里的人工验证模拟没有映射为持久化审批功能；正式版仍通过现有渠道原因与审计记录推进。未引入任意脚本执行或 Agent 运行日志。
- 操作指南已加入文档站「使用仓库工作区」。
