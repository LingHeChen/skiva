# Skiva 前端界面优化方案

版本：讨论稿 01 · 2026-10-21
配套交互原型：[prototype.html](../../prototype.html)

## 1. 建议结论

将当前按资源组织的管理控制台，升级为以发布任务为主线的交付工作台。保留现有仓库、流水线、Skills、快照、渠道、Profile 和客户端的数据模型，在界面上串联它们，让用户始终知道：**当前发生了什么、哪些内容会受影响、下一步应该做什么。**

优先改造发布和 Agent 接入，再统一通用列表与详情。原型是设计验证材料，全部使用模拟数据，不连接后端，不替换当前应用。无需安装依赖，直接在浏览器打开项目根目录的 `prototype.html`。

## 2. 当前问题及依据

本次结论来自代码和已有业务流程审阅，不是用户访谈或可用性统计。

| 当前实现                                                                             | 使用障碍                                                         | 建议                                                     |
| ------------------------------------------------------------------------------------ | ---------------------------------------------------------------- | -------------------------------------------------------- |
| `components/console.tsx` 的导航平铺仓库、Registry、流水线、快照、渠道、Profile、终端 | 首次使用时需要自己理解对象之间的关系                             | 按工作台、内容与校验、交付与治理分组；合并发布入口       |
| 概览主要展示资源数量、渠道和最近流水线                                               | 能看到系统里有什么，却难以判断下一步                             | 保留精简统计，主区域展示当前交付进度及下一步操作         |
| `ReleaseForm` 默认空集合，需要逐个选择版本                                           | 更新一个 Skill 时容易漏选其他已有 Skills，误把完整快照当增量补丁 | 从指定基线继承完整集合，显式展示保留、替换、移除         |
| 快照创建与渠道推进在独立页面                                                         | 用户不容易发现“创建成功但尚未交付”                               | 统一发布中心，保持创建、Canary、Stable 的显式分界        |
| Profile、客户端和渠道信息分散                                                        | 固定版本被误认为更新失败，授权被误认为已生效                     | 接入页关联 Profile、模式、目标快照，并区分目标与实际报告 |
| 大量详情和操作集中在同一 `console.tsx`                                               | 跨页面一致性和状态维护成本高                                     | 按领域拆分 Shell、页面、数据适配和通用组件               |
| 主品牌仍显示 `skills / enterprise` 和通用工作空间名                                  | 产品识别弱，真实组织上下文不明确                                 | 统一 Skiva 品牌；组织与用户信息来自真实会话              |

## 3. 信息架构

| 一级分组   | 页面                         | 原有能力映射                                  |
| ---------- | ---------------------------- | --------------------------------------------- |
| 工作台     | 交付概览                     | dashboard + 渠道状态 + 待处理事项             |
| 工作台     | 发布中心                     | 发布快照、完整集合、渠道推进、历史与回滚      |
| 内容与校验 | Skills 目录                  | Registry、版本、文件树、差异                  |
| 内容与校验 | Git 仓库                     | 平台托管 / 外部 Git、配置、ACL、PAT、托管策略 |
| 内容与校验 | 流水线                       | 运行记录、静态阶段、诊断、配置入口            |
| 交付与治理 | Agent 接入                   | Profiles、客户端、凭据生命周期、接入指引      |
| 交付与治理 | 审计记录                     | 发布、配置和授权操作记录                      |
| 底部工具   | 组织设置、个人账户、使用指引 | 保留现有成员、角色、安全与账户功能            |

合并导航入口不等于删除页面或 API。正式落地保留已有详情 URL 和深链接；旧入口可跳转到对应标签页。原型未覆盖完整组织设置和账户页面，仅展示主流程。

## 4. 核心交互设计

### 4.1 交付概览：下一步优先

- 顶部保留少量能够解释交付状态的数据：Skills、正式快照、授权客户端、待处理事项。
- 主卡展示指定候选变更的 Git → 校验 → 快照 → Canary → Stable 路径。
- 每个阶段提供明确的下一步入口，不把“流水线成功”写成“发布成功”。
- 将待发布版本、固定版本提醒、失败流水线放到可操作的关注列表。
- 初次进入且没有数据时，以“接入仓库 → 首次校验 → 创建快照”引导；不显示虚构趋势或零值成功率。

正式实现不能简单从“最近一次提交”推断整个组织的进度。先让用户选择要处理的候选版本或快照，依据实际资源关系派生状态；多仓库同时发布应分别呈现。

### 4.2 发布向导：默认保留，显式移除

1. **选择基线与完整集合**：默认使用目标正式渠道当前快照；首次发布无基线时从候选版本选择。自动保留其他 Skills，只替换用户选定的版本。
2. **审阅差异与诊断**：分别展示新增、更新、移除、未变更；移除项使用文字和颜色同时提示。调用真实 preview 接口，列出受影响 Profiles，审阅风险后才能继续。
3. **创建不可变快照**：展示确认摘要，创建成功后明确“渠道未改变”，提供推进 Canary 的下一步。
4. **Canary 验证**：核对挂载、重新加载 Skill、运行任务；“人工确认”与“自动验证结果”分别命名。
5. **推进 Stable**：使用与 Canary 相同的快照，显示影响范围并要求操作原因。
6. **回滚**：从该渠道历史选择目标，预览差异并填写原因；不重新构建内容。

如果预览后选择改变，立即使原预览和风险确认失效。提交时继续使用 generation 与幂等键。遇到 409 时保留用户选择，重新拉取渠道状态、重新预览；不自动重试覆盖。

原型中的 #023 / #024 仅为方便阅读的展示编号，正式实现使用现有不可变快照 ID，可用短 ID 展示并提供复制完整 ID，不默认引入新编号字段。

### 4.3 Agent 接入：解释一致性

- 用一行关联客户端、Profile、渠道、模式、授权状态、目标快照。
- pinned 固定版本显示解释提示，不作为错误红灯。
- 把实际挂载报告、最后通信时间、授权目标分开；没有遥测就显示“未获取”，不推断“在线”或“已生效”。
- 引导用户执行 `skills-mount status`、在任务边界重新固定、重新加载 Agent 上下文。
- 新客户端沿用 Token 仅展示一次的机制，提供复制与安全存储说明；撤销和轮换展示明确影响。

原型只展示目标快照与授权状态，没有捏造终端实时遥测，也不会执行终端命令。

### 4.4 流水线：诊断优先，明确配置范围

- 运行记录显示来源仓库、固定提交、状态、产出版本和详情入口。
- 失败页提供规则 ID、文件、行号及修复建议，而不是只有红色状态。
- 仓库根目录、`.skills-platform.yaml`、组织安全策略分别说明来源和优先级。
- 根目录修改属于仓库配置；禁止脚本分发等组织策略必须显示组织级影响，不能伪装成单仓库覆盖。
- 保持当前固定静态步骤。任意脚本、拖拽 DAG、CI 执行器不属于这轮前端优化。

原型的配置弹窗用于讨论入口和信息结构：保存只写入本页内存。正式版应分开保存不同作用域配置，并继续执行现有权限检查。

## 5. 视觉与组件规范

方向：**安静、清晰、具有工程工具质感的工作台**。沿用现有中文字体兼容性，减少装饰性 KPI 和重复卡片。

| 项目   | 建议                                                                       |
| ------ | -------------------------------------------------------------------------- |
| 背景   | 暖灰白 `#F5F5F0`，内容白 `#FFFFFF`，侧栏浅灰绿                             |
| 主文字 | 深墨 `#252A22`；辅助文字 `#73776C`                                         |
| 主操作 | 橄榄绿 `#54663B`；警告使用琥珀色，失败使用红色                             |
| 字体   | Avenir Next + PingFang SC / Microsoft YaHei；提交、ID、路径使用等宽字体    |
| 层级   | 页面标题 28–32px；区块标题 16–18px；正文 13–14px；辅助文字不承载关键操作   |
| 布局   | 桌面约 226px 侧栏；内容区限制最大宽度；12px 面板圆角，7px 控件圆角         |
| 状态   | 图标 + 文字 + 颜色，禁用按钮有对应的前置条件说明                           |
| 动效   | 短暂进入反馈；遵循 prefers-reduced-motion                                  |
| 表格   | 主字段突出、辅助字段减弱；大数据走服务端分页与筛选，不继续拉全量做本地分页 |

原型采用浅色作为首轮确认方向。正式改造需继续支持现有深色主题，独立校验语义色与对比度。

## 6. 响应式与可访问性

- 桌面显示侧栏和辅助摘要；中屏将摘要转为上下排列；手机收起侧栏。
- 表格允许局部水平滚动，页面本身不横向溢出。
- 正式端移动表单控件和主要按钮需满足足够点击面积。
- 原型包含键盘焦点、原生 dialog、Escape 关闭、必填原因校验、状态播报与减少动态效果支持。
- 生产验收补测完整 Tab 顺序、读屏表格语义、表单错误关联和对比度；原型自动检查不能替代无障碍验收。

## 7. 可行性与后端依赖

| 改动                         | 可复用能力                              | 是否需要补充后端                                                     |
| ---------------------------- | --------------------------------------- | -------------------------------------------------------------------- |
| 导航、视觉体系、领域组件拆分 | 现有路由与接口                          | 不需要                                                               |
| 完整集合默认继承             | 渠道当前快照、快照内容、版本列表        | 先核对字段覆盖；通常可前端组合                                       |
| 内容差异与发布预览           | Skill 版本差异、`/releases/preview`     | 复用；需处理缺失版本和分页                                           |
| 创建、推进、回滚             | releases / channels、generation、幂等键 | 不需要改变业务语义                                                   |
| Agent 目标与固定模式展示     | profiles / mount-clients / distribution | 目标展示可复用，不能替代真实遥测                                     |
| 跨页面“人工验证已完成”       | 原型仅内存状态                          | 若作为持久化门禁，需要新增验证记录、权限、审计；首期可仅做说明或引导 |
| “Agent 实际生效”判断         | 现有心跳或挂载状态应先逐项核对          | Agent 上下文 / 行为证明并非现成能力；不可仅由渠道状态推断            |
| 大规模搜索与联合筛选         | 现有游标 API                            | 需核对服务端筛选字段；不能由前端全量拉取掩盖性能问题                 |
| 多仓库交付任务卡             | 仓库、流水线、版本、快照关联            | 首期基于选定对象派生；跨会话任务持久化另行设计                       |

结论：主要体验改造具备现有数据基础，可分阶段落地。人工验证门禁、真实生效遥测和持久化任务管理必须作为明确的增量需求，不能通过前端假状态宣称已实现。

## 8. 实施顺序与验收

### 第一阶段：结构和视觉基础

拆分 Shell、导航、状态标签、列表和表单；统一 Skiva 品牌。保留现有权限、路由、错误与主题能力。验收所有旧入口仍可达，手机与桌面可用，无新增 API 行为差异。

### 第二阶段：发布主流程

实现基线继承、差异审阅、快照结果页和渠道操作。验收：更新单个 Skill 不会默认移除其他内容；未审阅不能提交；创建不推进渠道；Canary 与 Stable 独立；并发冲突需要重新确认；回滚只能选择授权历史目标。

### 第三阶段：接入与诊断

关联 Profiles / 客户端，改进 pinned 解释、流水线失败定位、接入指引。验收：用户能够区分已授权、目标快照、实际挂载、Agent 上下文；失败校验不能被标为生成了新版本。

### 第四阶段：整体回归

覆盖真实 API、角色差异、首发空状态、加载、接口错误、权限不足、快照冲突、撤权和恢复。执行现有 E2E 与文档构建，再补完整键盘 / 读屏验证。

建议在确认原型后再按阶段估算工期。首轮不同时重写后端、引入复杂设计系统或扩展流水线执行能力。

## 9. 本原型如何验收

推荐路径：概览 → 准备新发布 → 审阅差异 → 勾选确认 → 创建快照 → 推进 Canary（必填原因）→ 记录人工验证 → 推进 Stable → 回滚。

其他可体验内容：

- 取消选择 Skill，观察移除提示和完整集合数量。
- Skills 搜索无结果、查看文件和来源提交。
- Agent 接入中的 dynamic / pinned 目标变化。
- 流水线失败示例、诊断详情、配置弹窗。
- 左侧“重置演示”恢复初始状态；手机导航与键盘操作。

原型覆盖深度：发布主流程可完整操作；仓库接入、凭据与配置只提供局部示例和说明；组织管理、登录、真实遥测未展开。所有值均为演示数据，刷新后重置。

确认重点：导航分组是否容易理解、发布向导是否足够直观、页面密度是否合适、橄榄绿视觉方向是否符合 Skiva 的气质，以及是否需要把其他高频操作前置。
